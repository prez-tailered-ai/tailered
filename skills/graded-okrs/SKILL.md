# Graded OKRs

Google used OKRs from 1999: an objective with a few measurable key results, each graded from 0 to 1 at quarter end, with about 0.6 to 0.7 counted good, since a goal always fully met was set too low (Doerr, 2018). The 2004 founders' letter also gave engineers 20 percent of their time for their own projects. The guard: 20 percent time was reported as shrunk to "120 percent time" by 2013, and a key result can become the goal itself. Write the grades down and protect side time, or both are fiction.

## When to Activate

- Goals are set for a quarter or season, or read as tasks instead of numbers.
- A quarter ended and nobody graded the goals.
- The owner says OKRs, key results, 20 percent time or side projects.

Do not use for:
- what to work on this week: tailered-ai:mission-is-the-boss;
- a launch date: tailered-ai:two-date-plan.

## Inputs and outputs

Where to work: create a task folder, `artifacts/<skill name>-<YYYYMMDD>/` in the current project (this session's scratchpad if the project is read-only), and write the output there. Tables go in your reply.

Inputs: the owner's objectives, today's numbers, owners, quarter dates and weekly build hours.

Missing inputs never leave a blank. Put in a concrete proposal from what you know, mark it `proposal`, finish every step, and end with the one or two inputs that would change the result. A proposal is a real value: a dollar figure, a name, a date, a game, a list of likely items. Writing missing, pending, unknown, TBD or $X in its place is still a blank.

Output: `okrs.md`: objectives, key results, side-time share, grades and verdicts.

## Steps

Lead the reply with the key-results table (baseline, target, grade), then the verdict line, detail after.

### 1. Write objectives and key results

One to three objectives, each with two to four key results. Each is a number with a baseline, target, date and owner, such as graded projections on every NBA game each day, from 60 to 100 percent, by March 31 (proposal). A task is not a key result. The owner approves.

Completion: every key result has a number, baseline, target, date and owner.

### 2. Protect side time

Set a fixed share of weekly build hours for projects the owner chooses; proposal: 10 percent. Each gets a one-line goal and the usual release rules.

Completion: the share in hours per week and where it is recorded.

### 3. Grade at quarter end

Grade each key result 0.0 to 1.0 from its number, even when low. All 1.0 means targets too easy; under 0.3 needs a written reason.

Completion: every key result graded, with the number that decided it.

### 4. Verdict

For each objective write keep (carry forward), change (rewrite the key result for next quarter, never mid-quarter to save a grade) or stop. Compare side-time hours used with hours planned. Sharing the grades with the team or members is the owner's call; nothing here sends or posts.

Completion: a verdict word per objective, and side-time hours used against planned.

## Anti-Patterns

- Key results that are tasks.
- Rewriting a key result mid-quarter to make the grade.
- Hiding a low grade.
- Side time that exists only on paper.
