# Demo what ships

Tell the launch as a story, and show only what members will get. On 9 January 2007 Jobs introduced the iPhone as three devices, then revealed they were one. The guard: the iPhone was reported (Vogelstein, New York Times Magazine, 2013) to be so unfinished that the demo followed a rehearsed "golden path". At the company, every step on screen runs on the released build with today's data.

## When to Activate

- A live demo, walkthrough, recording or showing is planned.
- The owner says "demo it", "show them", "keynote" or "walk them through".
- A demo runs on a branch, a mock-up or hand-picked games.

Do not use for:
- the public launch explainer: tailered-ai:teach-every-launch;
- attention without ads: tailered-ai:story-not-ads;
- a public test of the model: tailered-ai:prove-it-in-public.

## Inputs and outputs

Where to work: create a task folder, `artifacts/<skill name>-<YYYYMMDD>/` in the current project (this session's scratchpad if the project is read-only), and write the output there. Tables go in your reply.

Inputs: the feature, the audience, the date, and the build members have now.

Missing inputs never leave a blank. Put in a concrete proposal from what you know, mark it `proposal`, finish every step, and end with the one or two inputs that would change the result. A proposal is a real value: a dollar figure, a name, a date, a game, a list of likely items. Writing missing, pending, unknown, TBD or $X in its place is still a blank. When you cannot open the page, file or data a step asks for, still fill every row: name the exact page, file or command to check and the value you expect there, marked `proposal`. Every row of every table gets a verdict word and an owner.

Output: `demo.md`: the story, the step table, the rehearsal and the owner's sign-off.

## Steps

Lead the reply with the step table, then the verdict line, then detail.

### 1. Write three beats

The member's problem, the turn, the proof on screen. One sentence each, such as: prices for one game sit on six sites; the main product puts the model beside all of them; here is tonight's Celtics game.

Completion: three sentences.

### 2. Tie every step to the shipped build

For each step, write the build it runs on, live or recorded data, and how the game was chosen. A step on a branch, mock-up or hand-picked game is cut, or said aloud as not yet shipped.

Completion: a table of steps, each with build, data and the word ship, label or cut.

### 3. Rehearse off the path

Run the demo on a game picked at random from today's slate, and on one failure state, such as a stale price or a game with no market. If either breaks, fix the product or cut the step.

Completion: the random game and the failure state named, with what happened.

### 4. Hand it to the owner

The numbers on screen must match the main product at that minute. The feature ships through tailered-ai:workflow and the release coordinator on the owner's word before it is shown as live. The owner approves the demo; this skill posts and sends nothing.

Completion: the demo file saved, the owner named as the approver, and the release route named.

## Anti-Patterns

- Demoing a branch as if members have it.
- Picking the game that makes the model look best.
- Numbers on screen that differ from the main product.
- A rehearsal that never leaves the scripted path.
